## 升级概述

FileShare 系统采用版本化升级机制，每个版本更新都提供独立的升级脚本，确保升级过程安全可靠。

### 版本号规则

系统版本号遵循语义化版本规范（Semantic Versioning）：
- **主版本号**（Major）：不兼容的 API 修改
- **次版本号**（Minor）：向下兼容的功能性新增
- **修订号**（Patch）：向下兼容的问题修正

例如：`1.0.1` 表示主版本 1，次版本 0，修订号 1。

### 升级脚本位置

所有升级脚本位于 `upgrades/` 目录：
```
upgrades/
├── README.md                    # 升级脚本说明
├── version.json                 # 版本管理文件
├── upgrade-v1.0.0-to-v1.0.1.js # 升级脚本
└── ...
```

## 升级前准备

### 1. 检查当前版本

运行以下命令查看当前版本：

```bash
npm run check-version
```

或直接查看版本文件：

```bash
cat upgrades/version.json
```

### 2. 备份数据

**⚠️ 重要：升级前必须备份数据！**

#### 备份数据库

```bash
# 方式一：使用管理后台备份（推荐）
# 进入 系统管理 > 数据备份 > 立即备份

# 方式二：使用命令行备份
npm run backup

# 方式三：手动备份
cp data/fileshare.db data/fileshare.db.backup.$(date +%Y%m%d_%H%M%S)
```

#### 备份存储文件

```bash
# 备份整个 storage 目录
cp -r storage storage.backup.$(date +%Y%m%d_%H%M%S)
```

#### 备份配置文件

```bash
# 备份环境变量文件
cp .env .env.backup.$(date +%Y%m%d_%H%M%S)
```

### 3. 停止系统服务

升级前必须停止所有系统服务：

**Linux/Unix**：
```bash
# 查找并停止 Node.js 进程
ps aux | grep node
pkill -f "node server/index.js"
pkill -f "vite"
```

**Windows**：
```powershell
# 查找并停止 Node.js 进程
Get-Process | Where-Object {$_.ProcessName -like "*node*"}
Stop-Process -Name node
```

**使用 PM2（如果使用）**：
```bash
pm2 stop all
```

### 4. 查看升级说明

在运行升级脚本前，请查看：
- 升级脚本中的更新内容说明
- 版本发布说明（如果有）
- 操作文档中的升级章节

## 执行升级

### 方式一：使用 npm 脚本（推荐）

```bash
npm run upgrade
```

### 方式二：直接运行升级脚本

```bash
# 从 v1.0.0 升级到 v1.0.1
node upgrades/upgrade-v1.0.0-to-v1.0.1.js
```

### 升级过程说明

升级脚本会自动执行以下步骤：

1. **检查版本**：验证当前版本是否符合升级要求
2. **备份数据库**：自动备份数据库文件
3. **验证文件**：检查升级所需的文件是否存在
4. **执行升级**：执行升级操作（代码更新、数据库迁移等）
5. **更新版本号**：更新版本管理文件
6. **验证结果**：验证升级是否成功

### 升级输出示例

```
========================================
  FileShare 系统升级脚本
  从 v1.0.0 升级到 v1.0.1
========================================

[步骤 1] 备份数据库
✓ 数据库已备份到: data/fileshare.db.backup.1234567890

[步骤 2] 验证升级文件
✓ 文件存在: client/src/components/FilePreview.tsx
✓ 文件存在: server/routes/files.js
✓ 所有升级文件验证通过

[步骤 3] 执行升级操作
✓ 代码更新已完成（通过 Git 拉取或手动更新）

[步骤 4] 更新版本号
✓ 版本已更新: 1.0.0 -> 1.0.1

[步骤 5] 验证升级结果
✓ 升级成功！当前版本: 1.0.1

========================================
  升级完成！
========================================
```

### 获取升级文件

升级脚本会验证文件是否存在，但不会自动更新代码。您需要：

**方式一：从 Git 仓库更新（推荐）**
```bash
git pull origin main
# 或切换到指定版本
git checkout v1.0.1
```

**方式二：手动下载升级包**
1. 从发布页面下载升级包
2. 解压并覆盖相应文件
3. 确保文件权限正确

## 回滚操作

如果升级后出现问题，可以回滚到旧版本：

### 1. 停止服务

```bash
# 停止所有服务
pkill -f node
# 或
pm2 stop all
```

### 2. 恢复数据库

```bash
# 找到备份文件
ls -la data/fileshare.db.backup.*

# 恢复数据库
cp data/fileshare.db.backup.1234567890 data/fileshare.db
```

### 3. 恢复代码

```bash
# 使用 Git 回滚
git checkout v1.0.0

# 或手动恢复文件
```

### 4. 恢复版本号

编辑 `upgrades/version.json`，将版本改回旧版本：

```json
{
  "currentVersion": "1.0.0",
  ...
}
```

### 5. 重启服务

```bash
npm run server:start
```

## 版本更新说明

### v1.0.10（2025-02-07）

在 v1.0.9 基础上的功能与修复，**无数据库结构变更**。拉取最新代码、重新构建前端并重启服务即可。

**本版本包含**：

- **空间内大文件上传**：空间详情页（文件树、文件列表、文件夹）增加「大文件上传（断点续传）」入口，上传目标自动为当前空间及当前选中文件夹。
- **下载与长耗时操作反馈**：文件下载、保存时显示「正在准备下载，请稍候…」，完成后提示「下载成功」或错误信息，避免长时间无反馈。
- **永久删除**  
  - 大文件永久删除：客户端请求超时延长至 2 分钟，服务端该接口请求超时延长至 3 分钟，避免大文件删除未完成即超时。  
  - 外键约束修复：永久删除时先删除/清理所有引用 `files(id)` 的表（`file_versions`、`permissions`、`comments`、`external_shares`、`chunk_uploads.file_id`），最后再删除 `files` 记录，解决 `SQLITE_CONSTRAINT: FOREIGN KEY constraint failed`。
- **登录与缓存**  
  - 进入受保护页前校验 token：从 localStorage 恢复登录态后，若有 token 会先请求 `/auth/me` 校验，失败则清除登录并跳转登录页，避免通过旧 token 或缓存直接访问 `/files` 等页面。  
  - 入口页防缓存：`index.html` 增加 `Cache-Control` / `Pragma`，减少浏览器强缓存导致使用旧前端逻辑。

**升级方式**：`git pull origin main` → `cd client && npm run build` → 重启服务。版本号可手动改为 `1.0.10`（见 `upgrades/version.json`），或保持 1.0.9 仅更新代码。

### 从 v1.0.7 直接升级到 v1.0.9（合并说明，2025-02-07）

支持从 **v1.0.7 或 v1.0.8** 一步升级到 **v1.0.9**，无需先升 1.0.8 再升 1.0.9。

**执行方式**：拉取最新代码后，在项目根目录执行 `npm run upgrade` 或 `npm run upgrade:1.0.9-from-1.0.7`，按提示完成备份、覆盖 client/src 与 server、安装依赖、构建前端与版本号更新，最后重启服务即可。

**本版本包含的更新（v1.0.8 + v1.0.9 合并）**：

- **空间卡片**：操作区（详情、成员、设置、删除）改为 flex 布局，避免重叠，便于后续扩展。
- **大文件上传**：修复初始化接口响应解构、按需取块避免大文件阻塞、用 ref 修复进度条与完成逻辑、message 由父组件传入、Select 根目录选项不再使用 `value={null}`、界面显示「正在初始化上传…」「正在合并文件…」；服务启动时自动为 `chunk_uploads` 表补全 `file_id` 列；分块上传完成时文件名按 UTF-8 保存（解决乱码）。
- **普通上传**：失败时提示「若文件较大请使用『大文件上传』」；支持选择上传目标空间与文件夹；「上传到」文案明确普通上传与大文件上传均生效，空间下拉为「选择空间（有权限的空间，可选）」。
- **上传目标**：普通上传与大文件上传均可选择「上传到」某空间及可选文件夹（有权限的空间列表）。
- **操作日志**：优先从 X-Forwarded-For、X-Real-IP 获取客户端 IP；若前置有 Nginx 等代理，需配置转发上述请求头。
- **时区**：统一为东八区北京时间。服务端强制 `TZ=Asia/Shanghai`；操作日志与库内其他表一致存 UTC；前端将无时区日期按 UTC 解析后按东八区展示。
- **其他**：FilePreview 移除调试用 console.log。
- **数据库**：首次启动时自动为 `chunk_uploads` 增加 `file_id` 列，无手动迁移。

**已处于 v1.0.8 的用户**：若仅需升级到 v1.0.9（不覆盖代码），可拉取代码后执行 `npm run upgrade:1.0.9` 更新版本号并重启服务。

### v1.0.7（2025-02-07）

- **UI 设计系统**：全局设计令牌（字体 Syne / Plus Jakarta Sans、青绿强调色、圆角与阴影）；登录页深色编辑风背景与动效；布局与工作台统一风格与微动效。
- **批量操作**：文件管理页、空间详情页（三处文件表）支持多选与批量移动、批量删除、从空间移除；回收站支持批量恢复与批量永久删除。
- **空间删除**：支持删除空间。仅管理员或空间所有者可删，且须先清空空间内所有文件和文件夹；删除前有步骤提示。
- **空间名称过长**：空间列表卡片与空间详情页标题、面包屑支持省略号显示，悬停可查看完整名称。
- **大文件上传**：单次表单上传默认上限 50MB（可配置 `SINGLE_UPLOAD_MAX`），超过则提示使用「大文件上传」；文件管理页提供「大文件上传（支持断点续传）」分块上传入口，避免大文件导致 500 或宕机。
- **操作日志**：IP 获取支持代理（X-Forwarded-For）并规范化 IPv6 映射 IPv4；时间统一为东八区北京时间（Asia/Shanghai）存储。
- **升级脚本**：项目部署根目录默认值改为 `/home/FileShare-main`（仍可手动输入其他路径）。
- 无数据库结构变更，升级后需重新构建前端并重启服务。从 v1.0.6 升级请执行：`npm run upgrade` 或 `npm run upgrade:1.0.7`。

## 常见问题

### Q1: 升级脚本执行失败怎么办？

**A**: 
1. 查看错误信息，确定失败原因
2. 检查备份文件是否完整
3. 确认文件权限是否正确
4. 尝试手动执行升级步骤
5. 联系技术支持

### Q2: 可以跳过版本升级吗？

**A**: 不建议跳过版本升级。每个升级脚本都针对特定版本设计，跳过可能导致：
- 数据库结构不匹配
- 功能异常
- 系统不稳定

### Q3: 升级需要多长时间？

**A**: 通常几分钟内完成，具体时间取决于：
- 数据库大小
- 文件数量
- 网络速度（如果从远程拉取代码）
- 升级操作的复杂度

### Q4: 升级会影响现有数据吗？

**A**: 
- 升级脚本会自动备份数据库
- 正常情况下不会影响现有数据
- 但建议升级前手动备份重要数据
- 如果升级包含数据库迁移，可能会修改数据结构

### Q5: 如何查看升级历史？

**A**: 查看 `upgrades/version.json` 文件中的 `upgradeHistory` 字段：

```bash
cat upgrades/version.json | grep -A 10 upgradeHistory
```

### Q6: 升级后需要重新安装依赖吗？

**A**: 
- 如果 `package.json` 中的依赖没有变化，不需要
- 如果依赖有更新，运行：
  ```bash
  npm install
  cd client && npm install && cd ..
  ```

### Q7: 升级脚本支持哪些操作系统？

**A**: 升级脚本使用 Node.js 编写，支持：
- Linux
- macOS
- Windows（需要 Git Bash 或 PowerShell）
